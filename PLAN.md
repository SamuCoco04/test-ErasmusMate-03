# ErasmusMate — PLAN.md

## Iteration 3 objective

Iteration 3 starts from an almost empty repository and aims to rebuild ErasmusMate as a higher-quality, test-first, full-stack MVP.

The goal is not only to generate code, but to produce a product that is:

- backend-backed
- frontend-complete
- locally runnable
- testable
- visually aligned with the Figma references
- simple enough for students and coordinators to understand
- efficient to use with the fewest reasonable clicks
- suitable to show to a tutor, client, or potential buyer

This iteration must avoid the main weaknesses observed in previous iterations:

- weak test coverage
- missing traceability between requirements/workflows and tests
- inconsistent documentation of decisions
- overly technical UI language
- too many clicks for common actions
- UI not close enough to the Figma/mockup quality
- Codex making implementation decisions without documenting them

This includes decisions about:

# 5. Development principles

## 5.1 Test-first / acceptance-first

Before implementing major functionality, create or update the relevant tests.

Some tests may fail initially because the feature does not exist yet. That is acceptable.

A phase is not complete until:

- relevant tests exist
- the traceability matrix is updated
- tests pass or deferred failures are documented

## 5.2 Workflow-first implementation

Implement by workflow, not by isolated screens.

A screen is not complete if it only displays UI without real workflow behavior.

Each important workflow must include:

- backend persistence
- validation
- role guards
- state transitions
- frontend journey
- test coverage
- traceability entry

## 5.3 Architecture-first inside each phase

Each phase must begin with a short architecture check before implementation.

Codex must identify:

- what modules will be created or modified
- what backend services are needed
- what API routes are needed
- what UI components are needed
- what tests must exist before or alongside the implementation
- what decisions must be recorded in DECISIONS.md

This architecture check should be brief but explicit.

Do not implement large functionality without first deciding the module boundaries, data flow, validation strategy, and testing approach.

## 5.4 Conventional commits

All commits must follow Conventional Commits.

Examples:

    feat(institutional): add student dashboard workflow
    feat(learning-agreement): implement row-level review
    fix(navigation): preserve demo context across shell links
    test(e2e): add coordinator review workflow scenario
    docs(decisions): record Prisma SQLite decision
    refactor(ui): extract reusable dashboard card
    style(shell): align navigation with Figma reference

Commits should be small, focused, and reviewable.

## 5.5 Decision documentation

Any meaningful decision must be recorded in DECISIONS.md.

This includes:

- technical decisions
- architecture decisions
- database decisions
- testing decisions
- UI/UX decisions
- workflow decisions
- deferred or rejected alternatives

No phase is complete until DECISIONS.md is updated.

## 5.6 Human-friendly UI language

Avoid technical or unusual words in the interface.

Do not expose implementation vocabulary to users.

Avoid labels such as:

- backend-visible
- workflow artifact
- route handler
- persisted entity
- governance surface
- policy-aware
- moderation-limited state

Prefer clear labels such as:

- visible recommendations
- needs correction
- review queue
- pending approval
- hidden after reports
- Learning Agreement
- Erasmus stay
- mark as reviewed

## 5.7 Minimum-click UX

Common actions should require the fewest reasonable clicks.

Examples:

- student sees the next pending task from the dashboard
- coordinator opens review items directly from dashboard or queue
- approve/reject actions are visible in the review detail
- denied Learning Agreement rows are easy to find and revise
- messaging opens directly from accepted connections
- map has filters, list, preview, and detail in one coherent flow

Do not add unnecessary intermediate pages.

# 7. Testing strategy overview

The test strategy has three levels.

## 7.1 E2E tests

Use Playwright.

Must cover the main user journeys:

- student dashboard and pending tasks
- submission flow
- coordinator review flow
- deadline flow
- exception request flow
- Learning Agreement flow
- Academic Summary flow
- student discovery
- connection request
- accepted-only messaging
- recommendations/tips/reviews
- reporting/moderation
- map-based discovery

## 7.2 Service/API/domain tests

Use Vitest where practical.

Must cover rules such as:

- invalid state transitions
- permissions and role guards
- deadline blocking
- exception decisions
- denied-row resubmission enforcement
- accepted-only messaging
- moderation visibility filtering
- map visibility filtering
- approved-row revision semantics

## 7.3 Smoke tests

Must validate:

- app boots
- seed works
- main routes load
- demo users work
- no critical 500 errors
- navigation preserves demo context
- main dashboards render

# 8. Traceability strategy

TRACEABILITY_TEST_MATRIX.md must link tests to workflows and requirements.

Each row should include:

- test ID
- workflow
- requirement or business rule
- actor
- test type
- scenario
- expected result
- status

Example:

| Test ID | Workflow | Requirement / Rule | Actor | Type | Scenario | Expected result | Status |
|---|---|---|---|---|---|---|---|
| E2E-INST-001 | Student submission | REQ Document Submission | Student | E2E | Student submits required document | Submission becomes SUBMITTED and audit event exists | Planned |

---

# 9. Per-phase execution rule

Every implementation phase must follow this order:

1. architecture check
2. test or test-plan update
3. implementation
4. validation
5. review/fix pass
6. update TRACEABILITY_TEST_MATRIX.md
7. update DECISIONS.md
8. commit using Conventional Commits

No phase should be considered complete if tests, traceability, and decisions are not updated.
